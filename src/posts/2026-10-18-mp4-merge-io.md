## 不要默认重编码

合并同一编码参数的 MP4，最省时的路径是 `-c copy`：容器层重新封装，音视频码流不重新编码。只要分辨率、编码器、时间基与像素格式一致，画质与文件体积都不会被二次损失。

差异明显：

| 策略 | CPU | 画质 | 适用场景 |
| --- | --- | --- | --- |
| `-c copy` + concat demuxer | 低 | 无损 | 同源录屏、分段素材 |
| 统一转码后拼接 | 高 | 有损 | 参数不一致、需要统一输出 |
| 逐段转码再 concat | 很高 | 多次损失 | 不推荐 |

## 文件列表是输入，不是命令

concat demuxer 需要一个文本文件，每行一个路径。路径里可能有空格、单引号或非 ASCII 字符，直接拼 shell 命令很容易出错。

```text
file '/data/recordings/part 01.mp4'
file '/data/recordings/part 02.mp4'
```

写入时对单引号做转义，并始终把文件列表放在临时目录。不要让用户输入进入 shell；`subprocess.run([...], shell=False)` 只传参数数组。

```python
def merge(files: list[Path], output: Path) -> None:
    with tempfile.NamedTemporaryFile("w", suffix=".txt", delete=False) as fh:
        for path in files:
            escaped = str(path).replace("'", "'\\''")
            fh.write(f"file '{escaped}'\n")
        list_path = Path(fh.name)

    cmd = [
        "ffmpeg", "-hide_banner", "-loglevel", "error",
        "-f", "concat", "-safe", "0",
        "-i", str(list_path), "-c", "copy", "-movflags", "+faststart",
        str(output),
    ]
    subprocess.run(cmd, check=True)
```

## 批量调度

批处理不应该把所有任务同时扔进进程池。FFmpeg 本身会吃满 CPU 与磁盘，并发过高只会让 IO 抖动，错误信息也会互相淹没。

- 串行执行，单任务失败时记录输入、输出、退出码与 stderr。
- 先写临时文件，成功后原子重命名，避免留下半成品。
- 对已存在的输出做显式覆盖策略，不静默跳过。
- 失败任务保留列表文件，便于单独复现。

## 失败恢复

常见失败不是“命令不会用”，而是输入不一致：

1. 分辨率或像素格式不同，`-c copy` 产生花屏或时间戳错乱。
2. 某段缺少音轨，concat 后音画不同步。
3. 路径包含换行或单引号，列表文件解析失败。
4. 输出目录与输入相同，临时文件被误扫进下一批。

工具应当先探测每段流的编码参数，再决定是否允许 `copy`。参数不一致时给出明确提示，而不是悄悄转码。自动转码可以作为显式选项，但不能是默认行为。

## 小结

`mp4_merger` 保持单文件 CLI：读路径、写列表、调用 FFmpeg、校验输出。复杂度集中在输入校验和失败诊断，而不是封装一个庞大的媒体框架。
